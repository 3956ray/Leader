# 调度与验收工作流

## 当前执行协议

以下业务原则继续有效。状态写入与通信步骤使用 [LOOP-V2.md](LOOP-V2.md)：`stage → send-intent → sent → ack → result → review`。只有状态转换工具写入权威账本和状态视图。用户已删除定时任务，改为交互式调度，不再创建或恢复定时任务。Leader发单后在当前运行中等待执行者回调、核验原始结果并续派，直到遇到真实人工门槛；不能只说“已派发”便结束，也不能承诺会在没有实际回调或新输入时自动工作。

## 1. 观察

调度者先读取三个真实状态：正式产品文档、产品仓库、两个协作任务。聊天摘要只能用于定位，不能作为 Checkpoint 证据。

## 2. 选择当前门禁

从最早没有通过证据的 Checkpoint 开始。后续工作已经存在时先保留并审计，不自动删除，也不把“已经写了代码”反向解释为门禁已通过。

## 3. 写单任务合同

`current-task.json` 必须只描述一个结果，并包含：

- `goal`：本轮结束时可判断真假的结果；
- `scope`：允许读取或修改的内容；
- `out_of_scope`：明确不做的后续事项；
- `acceptance`：逐项可验证门槛；
- `evidence_required`：文件、测试、真机记录或 diff；
- `stop_conditions`：必须停下并升级的问题。

只有 `leader_check.py` 通过且开发者任务空闲时才能下发。

## 4. 等待开发者

状态改为 `IN_PROGRESS`。开发者运行时只读取进度，不重复发送任务。开发者返回 `BLOCKED` 不等于失败；调度者应检查是否为产品决策、真实设备或权限等合理门禁。

## 5. 独立验收

调度者不直接接受“已完成”结论，而是核对：

1. 变更是否只在范围内；
2. 验收项是否逐项有证据；
3. 测试是否真的覆盖失败风险；
4. 是否违反 PRD、隐私或三步约束；
5. 是否引入未审查依赖；
6. 工作区是否混入无关修改。

证据充分时标记 `ACCEPTED`；可修复问题生成更小的 `REVISE` 任务；需求或门槛问题升级给产品经理。

## 6. 前进

只有当前 Checkpoint 的全部门槛被正式记录为通过，才能建立下一个 Checkpoint 的任务。调度者每轮结束都更新 `state.json`，保留已接受任务编号、证据路径和未验证项。

## 产品经理交接边界

工程选择只要不改变行为和边界，由开发者在任务范围内决定。产品经理只处理产品范围、用户路径、隐私、门槛和暂停条件。批准结果应先写入正式产品文档，再被调度者采用。
